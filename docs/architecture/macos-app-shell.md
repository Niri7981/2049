# macOS App 壳与本地服务生命周期

更新日期：2026-09-15。

## 选择

第一阶段选择 Electron 作为 macOS App 壳，继续用现有 Next.js/TypeScript 作为本地服务和展示层。SwiftUI 与 Tauri 都需要额外维护一套原生桥接或 Rust 构建链；当前产品重功能、不做精细原生视觉，Electron 能最小成本复用已验收的 TypeScript 付款后端。M7 打包前仍需完成签名、安装包和生产资源路径验证。

Electron renderer 只展示数据和提交有限的管理操作。它不能读取管理令牌、密钥、付款载荷或数据库，也不能请求任意 URL；preload 只暴露三个固定管理能力。所有钱包、额度、暂停、策略、预占、签名和记录均留在本地后端。

## 进程与认证

```text
Electron 主进程
├── BrowserWindow / Tray / 菜单
├── 每次启动生成的随机管理令牌
└── 启动一个仅绑定 127.0.0.1:3049 的 Next.js 子进程
      ├── 管理 API（Bearer 认证 + loopback + 跨站限制）
      ├── 产品钱包（macOS 钥匙串）
      └── app-ledger.sqlite（设置、预算与购买记录）
```

App 使用 macOS 单实例锁。第二次启动只唤起已有窗口，不启动第二个后端。关闭窗口时只隐藏窗口；菜单栏可重新打开。退出时先调用后端 `prepareQuit`，立即禁止新的购买、签名和提交，并等待已接受的购买及启动恢复操作结束后返回 `ready`；Electron 收到确认才终止并等待子进程退出。请求超时会重复等待同一收尾过程，不将超时视为可以强制终止签名器。

暂停写入后，付款在读取钱包后、模拟完成且实际调用签名器前、保存提交载荷前重新检查暂停、退出、额度及有效期。检查与实际签名器调用之间没有异步等待；已经开始的签名可能完成，但暂停后不会再提交其载荷。该顺序依赖 App 的单一付款服务拥有签名器。

启动健康检查会触发一次恢复，新购买等待这次检查结束。只有唯一服务实例在接受新购买前，才能把 `PAYING` 且没有持久载荷的崩溃记录标为提交前失败；有载荷的付款继续保留，使用原购买编号及原凭据查询，不重新签名或结算。暂停或关闭真实购买开关不阻止恢复已有付款。网络或配置不匹配时保留原状态，并返回 `recoveryStatus: pending`。

管理令牌只存在 Electron 主进程及其后端子进程环境。renderer 通过受限 IPC 请求固定路径，因此普通浏览器访问管理 API 会得到 401；只有 localhost 或 CORS 不能替代该认证。

## 钱包与数据

产品钱包使用固定钥匙串项目 `com.2049.wallet.v1 / consumer-wallet-v1`。首次启动创建后立即读回并核对公钥；之后永远从同一项目复用。钥匙串拒绝访问与“项目不存在”被区分，拒绝访问时不会偷偷生成替代钱包。

开发态实机首次启动创建的产品钱包地址是 `Hr937hUNE1yHzjDLhZngWn8rHUWGTuTRLMJoTzi9BUeH`。它与历史 Demo 钱包隔离，目前未充值；本文不包含私钥或签名载荷。

额度没有默认值。数据库以 test USDC 最小单位整数字符串接收和返回金额，设置与预算预占使用同一 SQLite 数据库事务。预算窗口使用系统当前时区：当前窗口保留已计算的真实午夜边界，临时切换时区不会立即获得新额度；时钟回拨也不会把窗口退回旧日期。跨过该边界后采用当时系统时区计算下一次午夜。

## M3 测试模式

App 只展示 Devnet 测试入口。默认 `simulated` 模式复用同一后端策略、额度事务、购买状态和账本，但不会加载签名器、构造交易或调用链上结算。重复购买编号返回原记录，不重复计费。

只有显式设置 `APP2049_ENABLE_DEVNET_PURCHASES=1` 时才进入原有 `runTask → x402 → executeApprovedPayment` 路径；该开关默认不存在。启用前仍必须核对产品钱包、公网 Devnet 配置、商家、余额和具体付款授权。第一阶段自动化和实机检查没有启用它。

## 付款与交付

`status=PAID` 表示原交易已经通过链上校验；独立的 `deliveryStatus` 表示 `NOT_PAID`（未确认付款）、`PENDING`（结果待恢复）或 `COMPLETE`（已交付）。链上确认先持久保存交易和消费日期，再读取结果；结果损坏或丢失不再把付款降级为未知。恢复交付沿用原消费日期，不重复计账。

交付状态从现有持久化的付款状态与结果字段得出，没有 SQLite schema 变更；旧已交付记录直接保持 `COMPLETE`。启动对每笔待恢复订单尝试一次恢复；持久化的 3–5 次自动交付重试仍属于 M5，本次没有把这一能力标为完成。
