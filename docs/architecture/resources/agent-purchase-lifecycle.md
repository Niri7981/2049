This stage unifies discovery, user registration, sample quoting, Spend Grants, purchase eligibility, x402 execution and delivery without adding a merchant executor. Mainnet signing remains subject to the existing fail-closed execution gate. No real transaction was used for this work.

## Four-blocker remediation (2026-10-08)

- Registration rejects HEAD/PUT/PATCH/DELETE and non-JSON POST at the backend boundary. Quote transport and the production signing gate independently reject historical unsupported methods; stored historical definitions remain readable.
- New discovery proposals and registrations use per-field descriptors. Query fields are strings; JSON body supports string, number, safe integer, boolean, null, object and array with bounded length/value/container constraints. Fixed fields cannot be overridden; undeclared inputs are rejected. The shared builder and saved-request validator cover discovery, sample quoting, Grant creation, purchase and execution. Existing array policies retain their original semantics and cannot be used for new registration.
- `/api/app/resources/prepare` is an authenticated local preview with no merchant I/O. Native confirmation shows the exact normalized destination, method, headers and composed body. The management command includes its request hash; backend reconstruction rejects changes. Agent routes and MCP schemas accept no approval flag or hash. Request authentication binds exact bytes and rejects nonce replay. Discovery confirmation does not create a resource, Grant, reservation or payment.
- POST Grant creation separately confirms the concrete sample and delegation of future requests under the immutable Resource policy. Additive migration `014_post_grant_consent` adds nullable `post_policy_hash` only. Existing grants and purchase evidence are preserved without inferred POST consent. New POST quotes/purchases require an active matching confirmed Grant before HTTP; signing rechecks the same policy. Recovery of already submitted/paid purchases still uses original evidence without repayment.
- Merchant HTTPS uses the unchanged pinned safe-fetch transport. IANA special-purpose IPv4 blocks are conservatively excluded; IPv6 allows ordinary global unicast in `2000::/3` while excluding its special-purpose blocks. Mixed DNS answers fail closed; redirects remain forbidden. Source registries and review date are in `public-resource-address.ts`.
- Resource bodies remain capped at 16 KiB of UTF-8. Resource/discovery/quote/purchase/Grant JSON envelopes have a separate 128 KiB streamed limit including metadata and JSON escaping; other local handlers retain 8 KiB. Full-size body and six-byte escaping regression tests exercise actual authenticated management and Agent handlers.

Current tests use isolated databases, mock merchant/RPC responses and fixture signers only. Targeted security regression: 7 files / 150 tests passed. Complete suite: 74 files / 930 tests passed. Native POST confirmation tests verify that opening and cancelling a review do not approve it, and only explicit discovery/Grant buttons fire approval. Native management DTO tests cover typed/legacy decoding and exact confirmation transport. Typecheck, lint, backend production and native Release builds passed. Actual installation verification is reported separately after updating the installed app. Official `@x402/core` and `@x402/svm` remain locked to 2.25.0; no second payment construction stack or merchant payment branch was added.

This remediation is not an architecture freeze decision or a real Mainnet purchase acceptance.
