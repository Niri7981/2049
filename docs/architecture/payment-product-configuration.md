# Installed payment configuration and readiness

The installed macOS app launches its bundled Node backend with a restricted child environment. The private `product-configuration.json` in the selected Application Support data directory is the persistent operator configuration. On first installation, the installer creates it with Mainnet execution disabled; upgrades preserve existing contents. The source checkout's `.env.local` is never used by the installed child.

The native launcher accepts only the explicit product keys for Mainnet execution, registered resource migration, wallet identity, Mainnet RPC and an optional facilitator URL. The backend validates environment, network, mint, wallet identity, active resource definitions and facilitator configuration when a purchase is requested. A user can select Mainnet and separately enable real execution through authenticated management control with a native confirmation. This setting creates no budget or Spend Grant.

For Mainnet buyer payments, the merchant's validated x402 quote supplies the fee payer. The merchant is responsible for its settlement facilitator. Yosh does not need a local facilitator URL to construct the official SDK payment payload. If an operator supplies an explicit URL, Yosh validates it and checks `/supported` against the bound quote sponsor. Devnet retains the official public test facilitator default; localnet requires an explicit loopback endpoint. Invalid configuration fails closed.

`get_spending_status` reports independent local prerequisites: environment, facilitator configuration, wallet, Daily Authority, registered resource, Spend Grant, Agent connection and service lifecycle. `transactionExecution.eligible` means these local predicates pass; it is not an assertion that a fresh merchant quote can settle. `get_market_quote` reports each registered resource's quote and read-only preflight, including recipient token account, buyer balance, fee payer and RPC chain checks. Its `requestInput` field identifies a required You.com search query. Neither tool signs, simulates or submits a transaction. The purchase path independently validates the same configuration and performs preflight before signing.

The built-in You.com Web Search request requires a bounded `query` in `request_purchase`. The backend attaches it only to the registered You.com HTTPS endpoint and binds the full request to the purchase ID. Reusing an ID with a different query is rejected. Existing resource registration, Grant, wallet and payment records are not rewritten.
